```
┌─────────────────────────────────────────────────────────────┐
│                    第 0 层：治理与监控层                       │
```

## 二、各层详细架构设计

### **第 0 层：治理与监控层**

#### 架构设计理念
```
设计原则：
├─ 统一入口：所有监控、告警、报告从此层发出
├─ 事件驱动：基于消息队列（Redis Pub/Sub）实现异步处理
├─ 智能决策：AI Agent 提供辅助分析，但不直接干预交易
└─ 可追溯性：所有决策和告警记录到 MongoDB

技术架构：
┌──────────────────────────────────────────────┐
│          AI Agent 智能引擎 (GPT-4)  │
└──────────────────────────────────────────────┘
              ↓           ↓           ↓
    ┌─────────────┬──────────────┬─────────────┐
    │  事前治理    │   事中监控    │  事后归因    │
    └─────────────┴──────────────┴─────────────┘
              ↓           ↓           ↓
    ┌─────────────────────────────────────────┐
    │   Redis (消息队列 + 实时指标缓存)         │
    └─────────────────────────────────────────┘
              ↓
    ┌─────────────────────────────────────────┐
    │   MongoDB (告警历史 + 分析报告 + 审计日志) │
    └─────────────────────────────────────────┘
```

#### 子模块设计

##### A. 事前治理模块
| 模块名称 | 职责 | 输入源 | 输出目标 | 存储位置 |
|---------|------|--------|---------|---------|
| **代码审查器** | 静态分析检测未来函数 | 策略代码文件 | 风险清单 | MongoDB (audit_logs) |
| **参数合规检查** | 验证风控参数范围 | 配置文件 | 通过/拒绝 | MongoDB (config_history) |
| **数据质量监控** | 检测缺失值、异常值 | Redis (data_status) | 质量报告 | MongoDB (data_quality) |
| **因子健康度诊断** | 评估因子 IC 衰减 | MongoDB (factor_metrics) | 健康度报告 | MongoDB (factor_health) |

##### B. 事中监控模块
| 模块名称 | 职责 | 监控频率 | 告警阈值 | 数据流 |
|---------|------|---------|---------|--------|
| **实时净值跟踪** | 计算组合净值曲线 | 盘中每分钟 | 日内回撤 > 3% | Redis → MongoDB |
| **风险暴露监控** | 行业/市值/Beta 暴露 | 每次调仓后 | 单行业 > 25% | Redis → 钉钉 |
| **异常交易检测** | 识别异常滑点 | 每笔成交后 | 滑点 > 2% | Redis → MongoDB |
| **持仓偏离告警** | 对比目标与实际 | 每日收盘后 | 偏离 > 5% | MongoDB → 钉钉 |

##### C. 事后归因模块
| 模块名称 | 职责 | 生成频率 | 输出格式 | 存储 |
|---------|------|---------|---------|------|
| **每日晨报生成** | 总结昨日 + 今日计划 | 每日 08:30 | Markdown | MongoDB (reports) |
| **Brinson 归因** | 拆解收益来源 | 每日收盘后 | JSON + 图表 | MongoDB (attribution) |
| **回撤归因分析** | 分析回撤原因 | 回撤 > 5% 时 | AI 报告 | MongoDB (incidents) |
| **周报/月报** | 完整绩效总结 | 周一/月初 | PDF | MongoDB (periodic_reports) |

#### 数据流设计
```
实时数据流（盘中）：
执行层 → Redis Pub/Sub (trade_events) 
       → 监控模块订阅 
       → 触发告警 
       → 钉钉推送 + MongoDB 记录

批处理数据流（盘后）：
MongoDB (历史数据) 
       → 归因模块计算 
       → AI Agent 生成报告 
       → MongoDB (reports) 
       → 定时推送

AI 分析流：
MongoDB
       → GPT-4 分析 
       → 结构化输出 
       → MongoDB + 钉钉
```

### **第 3 层：策略层**

#### 架构设计理念
```
设计原则：
├─ 规则明确：所有约束条件参数化配置
├─ 风险优先：先满足风控，再优化收益
├─ 可追溯：每次调仓决策记录到 MongoDB
└─ 灵活性：支持手动干预和紧急止损

技术架构：
┌──────────────────────────────────────────────┐
│          信号生成模块                          │
│   Signal Filtering                           │
└──────────────────────────────────────────────┘
              ↓
┌──────────────────────────────────────────────┐
│          组合优化模块                          │
│   Constraint Optimization (cvxpy)            │
└──────────────────────────────────────────────┘
              ↓
┌──────────────────────────────────────────────┐
│          风控检查模块                          │
│   Risk Exposure Check → Compliance           │
└──────────────────────────────────────────────┘
              ↓
┌──────────────────────────────────────────────┐
│          换手控制模块                          │
│   Buffer Mechanism → Turnover Control        │
└──────────────────────────────────────────────┘
              ↓
        MongoDB (target_positions) + Redis
```

#### 核心模块设计

##### A. 信号生成模块
```
输入：
├─ MongoDB: model:current（当前模型）
├─ MongoDB: factors（最新因子值）
└─ MongoDB: trade_status（交易状态）

处理流程：
1. 模型预测
   加载模型 → 预测所有股票得分 → 排序

2. 信号过滤
   剔除：ST、停牌、涨跌停、上市<60天、成交额<2000万

3. 信号输出
   MongoDB: signals
   {
       "signal_date": ISODate("2024-01-01"),
       "stock_code": "SH600000",
       "score": 0.85,
       "rank": 10,
       "created_at": ISODate("2024-01-01T08:00:00Z")
   }
```

##### B. 组合优化模块
```
优化目标：
最大化：Σ(score_i * weight_i)

约束条件：
1. 基础约束
   - Σ weight_i = 1
   - 0 ≤ weight_i ≤ 0.08（单票上限）
   - 15 ≤ count(weight_i > 0) ≤ 25（持仓数量）

2. 行业约束
   - Σ weight_i (industry=k) ≤ 0.25（单行业上限）
   - count(distinct industry) ≥ 5（行业分散）

3. 市值约束
   - Σ weight_i (market_cap < 10B) ≤ 0.30（小市值占比）

4. 换手约束（软约束）
   - |weight_new - weight_old| ≤ 0.30（单日换手）

求解器：cvxpy (ECOS 或 SCS)

输出：
MongoDB: target_positions
{
    "position_date": ISODate("2024-01-01"),
    "holdings": [
        {"stock_code": "SH600000", "target_weight": 0.05},
        ...
    ],
    "created_at": ISODate("2024-01-01T08:30:00Z")
}
```

##### C. 风控检查模块
```
检查项：
1. 暴露度检查
   - 单行业暴露 > 25% → 拒绝
   - 单票仓位 > 8% → 拒绝
   - 小市值占比 > 30% → 警告

2. 集中度检查
   - Top5 持仓占比 > 50% → 警告
   - 单一风格因子暴露 > 1σ → 警告

3. 流动性检查
   - 预计成交额 > 日均成交额 20% → 警告

检查结果：
MongoDB: risk_checks
{
    "check_date": ISODate("2024-01-01"),
    "status": "passed",  // passed / warning / rejected
    "issues": [
        {"type": "industry_exposure", "severity": "high", "detail": "..."}
    ],
    "created_at": ISODate("2024-01-01T08:35:00Z")
}
```

##### D. 换手控制模块（Buffer 机制）
```
逻辑：
1. 获取当前持仓
   Redis: position:current

2. 计算调整成本
   换手成本 = |新权重 - 旧权重| × 资金量 × 0.003

3. Buffer 判断
   IF 新股票得分 > 当前持仓最低分 × 1.15:
       换入
   ELSE:
       保持

4. 输出最终持仓
   MongoDB: final_positions
   Redis: position:target（供执行层使用）
```

### **第 4 层：执行层**

#### 架构设计理念
```
设计原则：
├─ 稳定性优先：执行失败有重试和降级机制
├─ 可追溯：每笔订单全程记录
├─ 低延迟：使用 XtQuant 直连券商
└─ 人工可干预：关键节点保留人工确认

技术架构：
┌──────────────────────────────────────────────┐
│          订单生成模块                          │
│   Position Diff → Order List                 │
└──────────────────────────────────────────────┘
              ↓
┌──────────────────────────────────────────────┐
│          XtQuant 执行接口                      │
│   Order Submission → Execution Monitor       │
└──────────────────────────────────────────────┘
              ↓
┌──────────────────────────────────────────────┐
│          成交回报处理                          │
│   Trade Confirmation → Reconciliation        │
└──────────────────────────────────────────────┘
              ↓
        MongoDB (orders) + Redis Pub/Sub
```

#### 核心模块设计

##### A. 订单生成模块
```
输入：
├─ position:target（目标持仓）
└─ position:current（当前持仓）

处理流程：
1. 计算持仓差异
   卖出列表：current - target
   买入列表：target - current

2. 生成订单
   MongoDB: orders
   {
       "order_id": "20240101001",
       "stock_code": "SH600000",
       "direction": "buy",
       "order_volume": 100,
       "order_price": null,  // 市价单
       "price_type": "market",
       "status": "pending",
       "created_at": ISODate("2024-01-01T09:25:00Z")
   }

3. 执行策略
   - 09:25-09:30：集合竞价卖出
   - 09:30-10:00：TWAP 分批买入
   - 14:30-15:00：尾盘补单
```

##### B. XtQuant 执行接口
```
核心功能：
1. 连接管理
   - 登录 QMT 客户端
   - 维持心跳连接
   - 断线重连

2. 订单提交
   xt_trader.order_stock(
       account=account_id,
       stock_code=stock_code,
       order_type=BUY/SELL,
       order_volume=volume,
       price_type=MARKET/LIMIT,
       price=price
   )

3. 订单监控
   - 实时查询订单状态
   - 部分成交处理
   - 废单重试

4. 成交回报
   - 订阅成交事件
   - 更新 MongoDB (orders)
   - 发布到 Redis Pub/Sub
```

##### C. 成交回报处理
```
处理流程：
1. 接收成交回报
   XtQuant 回调 → 解析成交信息

2. 更新订单状态
   MongoDB: orders (status = filled)

3. 更新持仓
   Redis: position:current（实时更新）
   MongoDB: positions（盘后归档）

4. 计算滑点
   实际成交价 - 预期价格 → 滑点分析

5. 发布事件
   Redis Pub/Sub: events:trade
   → 第0层监控模块订阅
   → 实时净值更新
```
